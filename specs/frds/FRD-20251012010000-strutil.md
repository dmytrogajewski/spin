## Overview

This FRD defines the implementation of `pkg/strutil`, a public package providing advanced string manipulation utilities for the Spin AI coding agent. The package focuses on operations needed for code manipulation, fuzzy matching, and text processing tasks essential for AI-driven file modifications.

---

## Motivation

### Why This Package?

1. **Foundation for patchapply**: The `internal/patchapply` package requires sophisticated string operations for:
   - Line-based file manipulation
   - Whitespace normalization
   - Context matching with fuzzy algorithms

2. **Reusable Across Project**: Placing utilities in `pkg/` makes them available to:
   - Internal packages (patchapply, filesearch)
   - External projects using Spin as a library
   - CLI tools

3. **Performance-Critical**: String operations are hot paths in:
   - Patch parsing (thousands of lines)
   - Fuzzy matching (file content comparison)
   - Indentation detection (every file edit)

---

## Goals

### Functional Goals

1. **Line Operations**: Split, join, and manipulate text lines
2. **Indentation Detection**: Auto-detect tabs vs spaces and indentation size
3. **Whitespace Normalization**: Handle different line endings and spacing
4. **Similarity Algorithms**: Implement Levenshtein distance and fuzzy matching
5. **Case Conversion**: Snake_case, camelCase, PascalCase utilities

### Non-Functional Goals

1. **Performance**: <100μs for typical operations
2. **Memory Efficiency**: Minimize allocations in hot paths
3. **Test Coverage**: ≥90%
4. **Cross-Platform**: Handle CRLF, LF, CR line endings
5. **No Dependencies**: Use only Go standard library

## Requirements

### Functional Requirements

#### FR-1: Line Operations

**FR-1.1: SplitLines**
- **Input**: Text string with mixed line endings (CRLF, LF, CR)
- **Output**: Slice of lines (string[])
- **Behavior**:
  - Normalize all line endings to `\n`
  - Preserve empty lines
  - Handle edge cases (empty string, no newlines)

**FR-1.2: JoinLines**
- **Input**: Slice of lines
- **Output**: Single string with `\n` line endings
- **Behavior**:
  - Join with `\n` separator
  - No trailing newline added by default

**FR-1.3: TrimEmptyLines**
- **Input**: Slice of lines
- **Output**: Slice with leading/trailing empty lines removed
- **Behavior**:
  - Remove only leading and trailing empty lines
  - Preserve empty lines in the middle
  - Return empty slice if all lines are empty

#### FR-2: Indentation Detection

**FR-2.1: DetectIndentation**
- **Input**: Source code text
- **Output**: `(useTabs bool, size int)`
- **Behavior**:
  - Analyze first 100 lines for indentation patterns
  - Count tabs vs spaces in leading whitespace
  - Determine most common indentation size
  - Default to spaces with size 4 if ambiguous
  - Handle mixed indentation gracefully

**FR-2.2: NormalizeIndentation**
- **Input**: Text, desired tab/space mode, size
- **Output**: Text with normalized indentation
- **Behavior**:
  - Convert tabs to spaces or vice versa
  - Maintain relative indentation levels
  - Preserve alignment in comments/strings

#### FR-3: Whitespace Handling

**FR-3.1: NormalizeWhitespace**
- **Input**: Text with irregular whitespace
- **Output**: Text with single spaces
- **Behavior**:
  - Replace multiple spaces with single space
  - Remove leading/trailing whitespace
  - Useful for fuzzy matching

**FR-3.2: TrimWhitespace**
- **Input**: Text
- **Output**: Trimmed text
- **Behavior**:
  - Remove leading and trailing whitespace
  - Wrapper around `strings.TrimSpace` for consistency

#### FR-4: Similarity Algorithms

**FR-4.1: LevenshteinDistance**
- **Input**: Two strings (a, b)
- **Output**: Edit distance (int)
- **Behavior**:
  - Implement dynamic programming algorithm
  - Count insertions, deletions, substitutions
  - Time complexity: O(n*m)
  - Space optimization: Use single array if possible

**FR-4.2: Similarity**
- **Input**: Two strings (a, b)
- **Output**: Similarity ratio (float64, 0.0-1.0)
- **Behavior**:
  - Calculate: `1.0 - (distance / max(len(a), len(b)))`
  - 1.0 = identical, 0.0 = completely different
  - Handle empty strings gracefully

**FR-4.3: FuzzyMatch**
- **Input**: Query string, target string
- **Output**: Match score (float64, 0.0-100.0)
- **Behavior**:
  - Score based on consecutive character matches
  - Case-insensitive matching
  - Earlier matches score higher
  - Used by filesearch package

#### FR-5: Case Conversion Utilities

**FR-5.1: ToSnakeCase**
- **Input**: `"MyVariableName"`
- **Output**: `"my_variable_name"`
- **Behavior**:
  - Convert camelCase/PascalCase to snake_case
  - Handle acronyms (HTTPServer → http_server)
  - Preserve existing underscores

**FR-5.2: ToCamelCase**
- **Input**: `"my_variable_name"`
- **Output**: `"myVariableName"`
- **Behavior**:
  - Convert snake_case to camelCase
  - First letter lowercase
  - Remove underscores

**FR-5.3: ToPascalCase**
- **Input**: `"my_variable_name"`
- **Output**: `"MyVariableName"`
- **Behavior**:
  - Convert snake_case to PascalCase
  - First letter uppercase
  - Remove underscores

### Non-Functional Requirements

#### NFR-1: Performance

- **NFR-1.1**: SplitLines <50μs for 1000-line file
- **NFR-1.2**: LevenshteinDistance <100μs for 100-char strings
- **NFR-1.3**: DetectIndentation <200μs for 100-line file
- **NFR-1.4**: Memory allocations minimized (prefer reusable buffers)

#### NFR-2: Quality

- **NFR-2.1**: Test coverage ≥90%
- **NFR-2.2**: All functions have godoc comments
- **NFR-2.3**: Table-driven tests for all functions
- **NFR-2.4**: Cyclomatic complexity ≤10 per function

#### NFR-3: Compatibility

- **NFR-3.1**: Support CRLF (Windows), LF (Unix), CR (old Mac)
- **NFR-3.2**: Handle UTF-8 text correctly
- **NFR-3.3**: Work on all major platforms (Linux, macOS, Windows)

### Implementation Details

#### SplitLines Algorithm

```go
func SplitLines(text string) []string {
    // 1. Normalize CRLF → LF, CR → LF
    text = strings.ReplaceAll(text, "\r\n", "\n")
    text = strings.ReplaceAll(text, "\r", "\n")

    // 2. Split on \n
    return strings.Split(text, "\n")
}
```

**Time Complexity**: O(n)
**Space Complexity**: O(n)
